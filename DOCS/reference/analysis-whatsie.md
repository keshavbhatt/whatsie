### Versioning
- Version is a hand-edited literal: `set(PROJECT_VERSION 5.1.0)` at `CMakeLists.txt:9` (set *outside* `project(... VERSION)`), then injected as `VERSIONSTR="5.1.0"` and `QApplication::setApplicationVersion(VERSIONSTR)` in `main.cpp:85`.
- Git hash/branch captured with `execute_process(git rev-parse ...)` at configure time; `string(TIMESTAMP ...)` embeds build time (non-reproducible builds). `def.h` provides `"unknown"` fallbacks.
- The same version must also be bumped manually in `dist/linux/com.ktechpit.whatsie.appdata.xml` `<releases>` (snap uses `adopt-info` + `parse-info` on that XML to derive the snap version), and `CHANGELOG.md` is generated by `go-semantic-release` in `.github/workflows/release.yml`. Three sources of truth.
- Windows: `dist/windows/whatsie.rc.in` gets `PROJECT_VERSION_RC` via `configure_file` (`CMakeLists.txt:226-231`).

## 2. Architecture

### Process/object model
- Single process (plus Chromium helper processes). `main()` creates `SingleApplication`, then `WebEngineProfileManager::instance()` (function-local static singleton), then a stack-allocated `MainWindow`, then wires IPC messages from secondary instances to `MainWindow` slots.
- `MainWindow` (split over 4 .cpp files) owns everything: tray, actions, web view, page, settings dialog, lock overlay, download manager, notification popup, rate dialog, auto-lock filter.
- Settings access is via `SettingsManager::instance().settings()` (a global `QSettings`) from **every** class — there is no settings model/abstraction; 30+ string keys are duplicated across files.

### God classes / mixed responsibilities
- **`MainWindow`** (≈1 300 LOC over 4 files, 40+ members): window + tray + actions + web engine lifecycle + notification presenter (3 backends) + theme application (Qt palette *and* page JS) + lock + auto-lock + download wiring + rate dialog + IPC targets + URL scheme handling + logout hacks. Splitting into 4 `.cpp` files did not separate responsibilities — every file touches the same members.
- **`SettingsWidget`** is simultaneously the view, the persistence layer (writes QSettings in every slot) *and* a controller (owns the automatic-theme timer, decides theme, drives lock setup dialogs). Its signals are emitted *by MainWindow* to trigger zoom (`mainwindow.cpp:91,96`) — inverted ownership.
- **`WebEnginePage`** mixes navigation policy, permission persistence, UI dialogs (blocking `exec()`), and JS injection.
- **`Utils`** is a `QObject` subclass used purely as a namespace for unrelated static functions; ~60 % of it is unused.

### Global state / singletons / statics
- `SettingsManager::instance()` — global `QSettings`, called ~150 times across all files.
- `WebEngineProfileManager::instance()` — function-local static owning a heap `QWebEngineProfile`, destroyed *after* `main()` returns, i.e. after `QApplication` is gone (`webengineprofilemanager.cpp:9-12,74-76`). Qt WebEngine requires profiles to be destroyed before the application; this is a latent crash/warning on exit.
- `common.cpp`: four global mutable variables (`defaultUserAgentStr`, `defaultAppAutoLockDuration`, `defaultAppAutoLock`, `defaultZoomFactorMaximized`), re-declared `extern` in `mainwindow.cpp:18-20` and `settingswidget.cpp:12-15` despite `common.h`.
- Function-local statics used as poor-man's async state: `getPageTheme()` (`mainwindow_webengine.cpp:392`), `isLoggedIn()` (`mainwindow_lock.cpp:168`), `triggerNewChat()` (`mainwindow.cpp:464`), static icons in `downloadwidget.cpp`.
- `Theme` static palettes; `Identicons` static colour table.
- `qApp->installEventFilter(m_autoLockEventFilter)` — application-wide filter.

## 6. Code-quality problems & anti-patterns (concrete)

### Memory / ownership / lifetime
1. `NotificationPopup` leak: `mainwindow.cpp:334` `new NotificationPopup(m_webEngine)` per app notification; `close()` without `WA_DeleteOnClose` only hides.
2. `doAppReload()` (`mainwindow_webengine.cpp:185-189`) creates a new `WebEnginePage` per reload; old pages remain children of the view; profile `downloadRequested` is connected again each time (`mainwindow_webengine.cpp:70`) → duplicate handlers.
3. `WebEnginePage::createWindow` (`webenginepage.cpp:47-51`) returns an unparented, viewless page → leak, and popups render nowhere.
4. `WebEngineProfileManager` static destroyed after `QApplication` (`webengineprofilemanager.cpp:9-12`).
5. `Utils::desktopOpenUrl` (`utils.cpp:379-400`): `QProcess` leaked when start fails; wrong fallback trigger.
6. `AutomaticTheme::m_gPosInfoSrc` uninitialised (`automatictheme.h:37`) and dereferenced in dtor (`automatictheme.cpp:70`) → crash when `QTimeZone` invalid path returns early.
7. `handleSelectClientCertificate` `certificates().at(0)` on possibly-empty list (`webenginepage.cpp:283`).
8. `WebView` ctor walks `parent()` chain until `objectName().contains("MainWindow")` with no null check, then `dynamic_cast` without null check (`webview.cpp:13-17`) — crashes if used anywhere else.
9. `DownloadManagerWidget m_downloadManagerWidget` is a *value member* of MainWindow shown as a top-level window; `DownloadWidget` keeps raw `QWebEngineDownloadRequest*` beyond its lifetime guarantees.
10. `Utils::~Utils() { this->deleteLater(); }` (`utils.cpp:7`) — calling deleteLater inside a destructor.
11. `RateApp` calls `this->deleteLater()` inside its own constructor (`rateapp.cpp:58,67`) while the caller continues to configure it (`mainwindow.cpp:485-500`).
12. `setNotificationPresenter` lambda captures `[&]` (`mainwindow_webengine.cpp:93`) — by-reference capture of locals in a long-lived callback (currently only `this` is used, but a future edit will dangle).
13. `NotificationPopup::present(...)` timer lambda `[&]` (`notificationpopup.h:106`).

### Async misuse / races
14. `isLoggedIn()` (`mainwindow_lock.cpp:167-182`) and `getPageTheme()` (`mainwindow_webengine.cpp:391-408`) return function-local statics that are updated later by `runJavaScript` callbacks — callers always see the previous value.

## 8. What was done right (carry forward)
